# Feature Specification: Данные RuMedBench — загрузка, канонические сплиты, EDA

**Feature Branch**: `001-data-pipeline`

**Created**: 2026-11-17

**Status**: Draft

**Input**: User description: "Выполни спеку 1" — спека 001 `data-pipeline` из `docs/ROADMAP.md`:
«Загрузка данных RuMedBench: скачать открытые сплиты (train/dev/test с метками) из
github.com/sb-ai-lab/MedBench для RuMedNLI, RuMedDaNet, RuMedTest (и NER/Top3/SymptomRec),
загрузить версию сайта из data/MedBench_data; единые схемы примеров; проверить пересечения
текстов сайта с open test; EDA и статистика для отчёта.»

## Контекст и обнаруженные факты

Проверка при подготовке спеки (2026-11-17) показала, что две версии данных **сильно
пересекаются**:

| Задача | Сплит сайта (`data/MedBench_data`) | Совпадает с открытым RuMedBench |
|---|---|---|
| RuMedNLI | train (12 627) | open train (11 222 из 11 232) + open dev (1 395) |
| RuMedNLI | dev (1 422) | **open test (1 421 из 1 422)** |
| RuMedNLI | test (1 536, без меток) | не пересекается — новые примеры |
| RuMedDaNet | train (1 308) | open train (1 052) + open dev (256) |
| RuMedDaNet | dev (256) | **open test (256)** |
| RuMedDaNet | test (512, без меток) | не пересекается |
| RuMedTest | test (397, без меток) | совпадает с open `private_test` — меток нет нигде |

Следствия:
- dev сайта — это открытый test. Использовать его для подбора чего-либо = подбор на test
  (нарушение принципа I конституции).
- Единственный честный набор для подбора — **открытый dev**.
- У RuMedTest нет размеченных данных: качество меряется только сабмитом на medbench.ru
  (там же получен previous art 35.0%).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Получить все данные одной командой (Priority: P1)

Участник команды на чистой машине одной командой получает все нужные данные: открытые сплиты
RuMedBench скачиваются из публичного репозитория, версия сайта читается из локальной папки
`data/MedBench_data`. Данные проверяются (число примеров, обязательные поля, допустимые метки),
и для каждой задачи становятся доступны примеры в едином виде.

**Why this priority**: без данных не работает ни одна следующая спека (оценка, бейзлайны, LLM).

**Independent Test**: на машине без скачанных данных выполнить команду загрузки и получить
отчёт с числом примеров по каждой задаче и сплиту, совпадающим с таблицей выше.

**Acceptance Scenarios**:

1. **Given** пустая папка данных, **When** участник запускает загрузку, **Then** открытые
   сплиты всех шести текстовых задач скачаны, проверены и сохранены локально, а в выводе — число
   примеров по задачам и сплитам.
2. **Given** данные уже скачаны и не изменились, **When** загрузка запускается повторно,
   **Then** ничего не скачивается заново и результат тот же.
3. **Given** скачанный файл повреждён или в нём не хватает полей, **When** выполняется
   проверка, **Then** загрузка завершается с понятной ошибкой, указывающей задачу, сплит и строку.
4. **Given** папки `data/MedBench_data` нет, **When** запускается загрузка, **Then** открытые
   данные всё равно загружаются, а про отсутствие данных сайта выводится предупреждение.

---

### User Story 2 - Канонические сплиты без утечек (Priority: P1)

Участник, который подбирает модель или промпт, получает данные по **роли** сплита, а не по
источнику: «обучение», «подбор» (dev), «финальная оценка» (test с метками), «сабмит»
(закрытый test сайта). Система сама гарантирует, что примеры финальной оценки не попадают в
обучение и подбор, и показывает отчёт о пересечениях.

**Why this priority**: честная оценка — неотменяемый принцип I; ошибка здесь обесценивает
любой SotA.

**Independent Test**: запросить сплиты по ролям для RuMedNLI и RuMedDaNet и убедиться, что
пересечение «финальной оценки» с «обучением» и «подбором» равно нулю, а отчёт о пересечениях
воспроизводит таблицу из раздела «Контекст».

**Acceptance Scenarios**:

1. **Given** загруженные данные, **When** участник запрашивает роль «подбор» для RuMedNLI,
   **Then** он получает открытый dev (1 395 примеров) и ни одного примера из открытого test.
2. **Given** загруженные данные, **When** запрашивается роль «обучение», **Then** в неё не
   входит ни один пример, текст которого совпадает с примером «финальной оценки» (в том числе 2
   примера RuMedNLI из train сайта, совпадающие с open test, — поэтому train сайта в обучение
   не берётся).
3. **Given** загруженные данные, **When** запрашивается роль «сабмит», **Then** возвращается
   закрытый test сайта без меток с исходными идентификаторами примеров.
4. **Given** загруженные данные, **When** формируется отчёт о пересечениях, **Then** для каждой
   пары (сплит сайта, открытый сплит) указано число совпадающих примеров.
5. **Given** RuMedTest, **When** запрашивается «финальная оценка», **Then** система явно
   сообщает, что размеченных данных нет и оценка возможна только сабмитом.

---

### User Story 3 - Статистика датасета для отчёта (Priority: P2)

Участник, пишущий раздел «Dataset» отчёта, получает готовые таблицы и графики: размеры
сплитов, распределение меток, длины текстов, примеры из каждой задачи, результаты проверки
пересечений.

**Why this priority**: раздел описания датасета даёт 10 баллов, но не блокирует следующие спеки.

**Independent Test**: запустить построение статистики и получить файл-отчёт с таблицами по всем
задачам, пригодный для вставки в отчёт.

**Acceptance Scenarios**:

1. **Given** загруженные данные, **When** запускается построение статистики, **Then**
   создаётся отчёт с размерами сплитов, распределением меток и длин текстов по каждой задаче.
2. **Given** отчёт построен, **When** участник сравнивает размеры открытых сплитов с таблицей
   статьи RuMedBench, **Then** они совпадают (отличия, если есть, явно перечислены в отчёте).

---

### User Story 4 - Расширенные задачи (Priority: P3)

Участник получает в том же едином виде задачи расширения — RuMedNER, RuMedTop3,
RuMedSymptomRec — чтобы позже посчитать полный Overall.

**Why this priority**: нужны только для полного Overall; ядро проекта — NLI, DaNet, RuMedTest.

**Independent Test**: запросить train/dev/test любой задачи расширения и получить примеры с
метками в едином виде.

**Acceptance Scenarios**:

1. **Given** загруженные данные, **When** запрашивается RuMedNER, **Then** каждый пример
   содержит токены и метки той же длины.
2. **Given** загруженные данные, **When** запрашивается RuMedTop3 или RuMedSymptomRec,
   **Then** каждый пример содержит текст жалоб и целевой код/симптом.

### Edge Cases

- Публичный репозиторий недоступен или изменился (файл удалён, новая версия): загрузка падает
  с понятной ошибкой; зафиксированная версия источника и контрольные суммы позволяют заметить
  подмену данных.
- В источнике встречаются дубликаты примеров внутри одного сплита: они учитываются в отчёте,
  но не удаляются молча.
- Одинаковый текст с разными метками в разных сплитах: попадает в отчёт о пересечениях как
  конфликт.
- Пример совпадает с open test только после нормализации пробелов/регистра: проверка
  пересечений учитывает такую нормализацию.
- Пустые или слишком длинные тексты: отражаются в статистике, не ломают загрузку.
- ECG2Pathology (архивы сигналов в `data/MedBench_data`): игнорируется без ошибки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST загружать открытые сплиты RuMedBench (train/dev/test, а для RuMedNLI,
  RuMedDaNet и RuMedTest — также `private_test`) для шести текстовых задач: RuMedNLI, RuMedDaNet,
  RuMedTest, RuMedNER, RuMedTop3, RuMedSymptomRec — из публичного репозитория с
  зафиксированной версией (коммитом).
- **FR-002**: Система MUST читать данные сайта из `data/MedBench_data` для RuMedNLI, RuMedDaNet
  и RuMedTest; при отсутствии папки — предупреждение без ошибки.
- **FR-003**: Система MUST проверять каждый файл: число примеров, обязательные поля,
  допустимые значения меток (NLI: entailment/contradiction/neutral; DaNet: да/нет; NER: токены и
  метки одинаковой длины), уникальность идентификаторов — и останавливаться с ошибкой,
  указывающей задачу, сплит и строку.
- **FR-004**: Система MUST представлять примеры всех задач в едином виде: идентификатор,
  задача, сплит, источник, входные поля задачи, метка (если есть).
- **FR-005**: Система MUST предоставлять сплиты по ролям: «обучение», «подбор», «финальная
  оценка», «сабмит». Для ядра: обучение = open train, подбор = open dev, финальная
  оценка = open test, сабмит = test сайта (он побайтово совпадает с открытым `private_test`).
  Данные сайта в роли не входят — используются только для отчёта о пересечениях и сверки.
- **FR-006**: Система MUST исключать из «обучения» и «подбора» любой пример, совпадающий по
  тексту (после нормализации пробелов и регистра) с примером «финальной оценки».
- **FR-007**: Система MUST формировать отчёт о пересечениях между всеми сплитами сайта и
  открытыми сплитами, включая конфликты меток.
- **FR-008**: Система MUST явно сообщать, что для RuMedTest нет размеченных данных и роль
  «финальная оценка» для него недоступна (только «сабмит»).
- **FR-009**: Повторная загрузка MUST быть идемпотентной: уже скачанные и проверенные (по
  контрольной сумме) файлы не скачиваются заново.
- **FR-010**: Система MUST строить отчёт со статистикой датасета: размеры сплитов,
  распределение меток, длины текстов, по 1–2 примера на задачу, сравнение размеров с таблицей
  статьи.
- **FR-011**: Загрузка и статистика MUST запускаться одной командой каждая.
- **FR-012**: Скачанные данные MUST храниться вне git (в игнорируемой папке данных).

### Key Entities

- **Задача (Task)**: одна из шести задач RuMedBench; тип (NLI, бинарный QA, множественный
  выбор, NER, многоклассовая классификация), набор допустимых меток, метрики.
- **Пример (Example)**: идентификатор, задача, исходный сплит, источник (open / site), входные
  поля (например, посылка и гипотеза; контекст и вопрос; вопрос и 4 варианта; токены; текст
  жалоб), метка или её отсутствие.
- **Источник (Source)**: открытый RuMedBench (версия = коммит репозитория) или сайт
  medbench.ru (локальная копия); контрольные суммы файлов.
- **Роль сплита (Split role)**: обучение / подбор / финальная оценка / сабмит — набор примеров
  задачи с гарантией отсутствия утечек.
- **Отчёт о пересечениях (Overlap report)**: матрица «сплит сайта × открытый сплит» с числом
  совпадений и конфликтами меток.
- **Статистика датасета (Dataset stats)**: таблицы и графики для раздела «Dataset» отчёта.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Участник на чистой машине получает все данные одной командой менее чем за
  5 минут при обычном интернет-соединении.
- **SC-002**: Число примеров в каждом открытом сплите совпадает с опубликованным в статье
  RuMedBench (для RuMedNLI: 11 232 / 1 395 / 1 422; для RuMedDaNet: 1 052 / 256 / 256) —
  100% задач ядра.
- **SC-003**: Пересечение «финальной оценки» с «обучением» и «подбором» равно 0 примеров для
  каждой задачи.
- **SC-004**: Отчёт о пересечениях воспроизводит таблицу раздела «Контекст» (±0 примеров).
- **SC-005**: Повторный запуск загрузки без изменений источника завершается менее чем за
  10 секунд без сетевых скачиваний.
- **SC-006**: Отчёт со статистикой покрывает 6 из 6 задач и может быть вставлен в раздел
  «Dataset» без ручного пересчёта.

## Assumptions

- Источник открытых данных — github.com/sb-ai-lab/MedBench (Apache-2.0); файлы RuMedNLI
  доступны там напрямую (проверено 2026-11-17), отдельный доступ к PhysioNet не нужен.
- Версия сайта уже лежит у участника в `data/MedBench_data` (раздаётся вручную); спека её не
  скачивает.
- ECG2Pathology вне скоупа (ADR-007).
- train сайта ≈ open train + open dev (для RuMedNLI: 11 222 + 1 395 + 10 новых примеров, ещё
  2 совпадают с open test), а test сайта побайтово равен открытому `private_test`. Поэтому
  единственный источник примеров — открытый репозиторий; данные сайта нужны только для сверки
  и отчёта о пересечениях (research R2).
- Нормализация для поиска пересечений: схлопывание пробелов, нижний регистр, обрезка по краям;
  более агрессивная (лемматизация, near-duplicates) — вне скоупа.
- Вывод на ролях «подбор = open dev» меняет формулировку «dev сайта» в `docs/ROADMAP.md`
  (спека 004) — требуется обновить ROADMAP и холст «02 Data & Evaluation» (ADR-012) на этапе
  `/speckit-plan`.
