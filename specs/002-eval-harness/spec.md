# Feature Specification: Харнесс оценки — метрики как в статье, реестр прогонов, сабмит

**Feature Branch**: `002-eval-harness`

**Created**: 2026-11-17

**Status**: Draft

**Input**: User description: "Переходи к следующей спеке" — спека 002 `eval-harness` из
`docs/ROADMAP.md`: «Метрики (Acc, Hit@3, macro-F1, Overall как в статье); формат
`results/<run_id>/preds.jsonl` + `meta.json`; сводная таблица vs previous art; экспорт сабмита
для medbench.ru».

## Контекст

- Официальная оценка RuMedBench — скрипт `code/eval.py` открытого репозитория (коммит
  `dd57f4f`): Accuracy для NLI и DaNet; Accuracy и Hit@3 (верная метка среди трёх предсказанных)
  для Top3 и SymptomRec; для NER — потокенная accuracy и F1 по сущностям; Overall — среднее по
  пяти задачам, где у задач с двумя метриками они сначала усредняются. Все числа — в процентах.
- В том же репозитории лежат предсказания моделей статьи (`code/naive`, `code/linear_models`,
  `code/bilstm`, `code/bert`, `code/human`) — по ним можно проверить, что наш подсчёт совпадает
  с опубликованной таблицей.
- Закрытый тест сайта medbench.ru принимает zip с файлами `RuMedDaNet.jsonl`
  (`pairID`, `answer`), `RuMedNLI.jsonl` (`pairID`, `gold_label`), `RuMedTest.jsonl`
  (`idx`, `answer` ∈ "1"…"4") — образец `lb_submissions/SAI/Naive/sample_submission.zip`.
- Данные и роли (`train`/`tune`/`final`/`submit`) даёт спека 001; подбор — только на `tune`,
  `final` — один финальный прогон на конфигурацию (конституция, принцип I).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Посчитать метрики ровно как в статье (Priority: P1)

Участник, получивший предсказания любым подходом (бейзлайн, LLM, дообученный энкодер), считает
метрики задачи на роли `tune` или `final` и получает те же числа, что дал бы официальный скрипт
оценки RuMedBench.

**Why this priority**: без сравнимых метрик нельзя заявить SotA — это основа бонуса до 25 баллов.

**Independent Test**: прогнать оценку по предсказаниям моделей статьи из открытого репозитория и
получить таблицу, совпадающую с таблицей 3 статьи (до 0.01 п.п.).

**Acceptance Scenarios**:

1. **Given** предсказания для всех примеров роли `final` задачи RuMedNLI, **When** участник
   запускает оценку, **Then** он получает Accuracy в процентах с двумя знаками.
2. **Given** для RuMedTop3 по три упорядоченные метки на пример, **When** запускается оценка,
   **Then** выводятся Accuracy (по первой метке) и Hit@3.
3. **Given** для RuMedNER по тегу на каждый токен, **When** запускается оценка, **Then**
   выводятся потокенная accuracy и F1 по сущностям, как в официальном скрипте.
4. **Given** предсказания моделей статьи (naive, TF-IDF, BiLSTM, RuBERT, человек) для пяти
   задач, **When** запускается оценка, **Then** все метрики и Overall совпадают с таблицей
   статьи с точностью до 0.01.
5. **Given** предсказаний меньше, чем примеров в роли, или есть лишние/чужие идентификаторы,
   или недопустимая метка, **When** запускается оценка, **Then** оценка останавливается с
   ошибкой, где перечислены проблемные идентификаторы.

### User Story 2 - Единый формат и реестр прогонов (Priority: P1)

Участник сохраняет результат прогона в стандартном виде: предсказания по примерам и описание
прогона (подход, модель и её версия, задача, роль, конфигурация, коммит кода, дата, метрики,
для LLM — токены и доля невалидных ответов). Все прогоны команды видны в одном месте.

**Why this priority**: принцип II (воспроизводимость) и общий формат для спек 003–009.

**Independent Test**: сохранить прогон, затем в чистой сессии по одной лишь папке прогона
пересчитать метрики и восстановить, чем и на каких данных он получен.

**Acceptance Scenarios**:

1. **Given** предсказания и описание прогона, **When** участник сохраняет прогон, **Then**
   появляется папка прогона с предсказаниями и описанием, метрики посчитаны и записаны.
2. **Given** сохранённый прогон, **When** метрики пересчитываются заново, **Then** они
   совпадают с записанными.
3. **Given** прогон на роли `final` для конфигурации, у которой уже есть `final`-прогон,
   **When** участник пытается сохранить ещё один, **Then** система отказывает и объясняет
   принцип «один финальный прогон на конфигурацию»; повтор возможен только с явным
   обоснованием, которое записывается в описание прогона.
4. **Given** прогон с невалидными ответами LLM, **When** он сохраняется, **Then** доля
   невалидных ответов записана и видна в сводке.

---

### User Story 3 - Сводная таблица против previous art (Priority: P2)

Участник одной командой получает таблицу всех прогонов на `final`: наши результаты рядом с
опубликованными (бейзлайны статьи, RuBioRoBERTa, ChatGPT, человек), с отметкой, где мы лучше
лучшего опубликованного результата, и Overall там, где есть все пять задач.

**Why this priority**: главный артефакт для раздела результатов отчёта, но опирается на US1–US2.

**Independent Test**: при наличии нескольких прогонов построить таблицу и проверить, что
лучшие результаты отмечены, а previous art совпадает с `docs/ROADMAP.md`.

**Acceptance Scenarios**:

1. **Given** прогоны на `final`, **When** строится сводка, **Then** для каждой задачи видны
   наши метрики, лучший опубликованный результат и разница в п.п.
2. **Given** прогоны на `tune`, **When** строится сводка, **Then** они показываются отдельной
   таблицей «разработка» и не смешиваются с финальными.
3. **Given** у подхода есть финальные прогоны не для всех пяти задач, **When** строится
   сводка, **Then** Overall для него не считается (прочерк), а не считается по неполному набору.

### User Story 4 - Сабмит на medbench.ru (Priority: P2)

Участник собирает архив для закрытого лидерборда из прогонов на роли `submit` для RuMedDaNet,
RuMedNLI и RuMedTest и получает готовый к загрузке файл в формате образца сайта.

**Why this priority**: RuMedTest оценивается только так; сабмит — бонус к отчёту.

**Independent Test**: собрать архив из прогонов `submit` и сравнить его структуру с образцом
`sample_submission.zip` (имена файлов, поля, число строк, допустимые значения).

**Acceptance Scenarios**:

1. **Given** прогоны `submit` для трёх задач, **When** участник собирает сабмит, **Then**
   получается архив с тремя файлами, по строке на каждый пример закрытого теста, с теми же
   идентификаторами и в формате образца.
2. **Given** нет прогона `submit` для одной из задач, **When** собирается сабмит, **Then**
   участник получает предупреждение и может собрать архив без неё (или с наивным ответом —
   только по явному флагу).
3. **Given** собранный архив, **When** проверяется его формат, **Then** все идентификаторы
   закрытого теста присутствуют ровно по одному разу, значения допустимы.

### Edge Cases

- Предсказания для RuMedTest пытаются оценить локально → понятный отказ: меток нет, только сабмит.
- В предсказаниях Top3/SymptomRec меньше или больше трёх меток → ошибка (Hit@3 определён для
  ровно трёх; меньше трёх — ошибка, дубликаты внутри тройки — ошибка).
- Длина предсказанной последовательности NER не совпадает с числом токенов → ошибка с
  идентификатором примера.
- Метка вне допустимого множества (например, «maybe» для NLI) → ошибка; невалидные ответы LLM
  должны быть заменены резервной меткой ещё до оценки (это делает подход, а не харнесс).
- Роль `tune` для задач, где метки `tune` после очистки дубликатов (ADR-014) отличаются по
  размеру от исходного dev → оценка идёт по роли, а не по исходному файлу.
- Предсказания, сохранённые для старой версии данных (другой коммит источника) → отказ с
  объяснением.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST считать метрики задач так же, как официальный скрипт RuMedBench:
  Accuracy (NLI, DaNet, Top3, SymptomRec), Hit@3 (Top3, SymptomRec), потокенную accuracy и F1 по
  сущностям (NER); в процентах.
- **FR-002**: Система MUST считать Overall как среднее пяти задач (RuMedTop3, RuMedSymptomRec,
  RuMedDaNet, RuMedNLI, RuMedNER) с предварительным усреднением двух метрик задачи; при
  отсутствии хотя бы одной задачи Overall не считается.
- **FR-003**: Система MUST проверять полноту и корректность предсказаний относительно роли:
  каждый пример роли ровно один раз, нет лишних идентификаторов, значения допустимы.
- **FR-004**: Система MUST отказывать в локальной оценке RuMedTest и любой роли `submit`.
- **FR-005**: Система MUST хранить прогон как папку с предсказаниями и описанием: идентификатор
  прогона, подход, модель и её версия/тег, задача, роль, конфигурация, коммит кода, версия
  данных (коммит источника), дата, метрики, а для LLM — токены, задержка и доля невалидных
  ответов.
- **FR-006**: Система MUST обеспечивать правило «один `final` на конфигурацию»: повторный
  финальный прогон той же конфигурации отклоняется, если не указано обоснование; обоснование
  сохраняется в описании прогона и видно в сводке.
- **FR-007**: Система MUST строить сводные таблицы (финальная и разработка) по всем прогонам с
  previous art, разницей в п.п., отметкой SotA и Overall для полных наборов.
- **FR-008**: Previous art MUST храниться в одном файле-источнике с указанием публикации для
  каждой цифры (статья, README репозитория, lb_submissions).
- **FR-009**: Система MUST собирать архив сабмита для medbench.ru из прогонов `submit` в формате
  образца сайта и проверять его перед записью.
- **FR-010**: Система MUST уметь оценивать предсказания в формате выходных файлов официального
  репозитория (поля `prediction` рядом с меткой), чтобы воспроизвести таблицу статьи.
- **FR-011**: Все операции (оценка, сохранение прогона, сводка, сабмит) MUST быть доступны
  одной командой каждая и программно — для использования из спек 003–009.

### Key Entities

- **Предсказание (Prediction)**: идентификатор примера и ответ подхода: метка (NLI, DaNet,
  RuMedTest), упорядоченная тройка меток (Top3, SymptomRec) или последовательность тегов (NER);
  опционально — флаг невалидного ответа и сырой ответ модели.
- **Прогон (Run)**: набор предсказаний одного подхода для одной задачи и роли + описание
  (подход, модель, конфигурация, версии кода и данных, дата, метрики, затраты).
- **Метрики задачи (Task metrics)**: одно или два числа в процентах по правилам статьи.
- **Previous art**: опубликованные результаты по задачам с источником.
- **Сводка (Leaderboard)**: таблицы финальных и разработческих прогонов против previous art.
- **Сабмит (Submission)**: архив для medbench.ru из прогонов `submit`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оценка предсказаний пяти моделей статьи (naive, TF-IDF, BiLSTM, RuBERT, человек)
  воспроизводит все числа таблицы 3 статьи и официального скрипта с расхождением ≤ 0.01 п.п.
- **SC-002**: Пересчёт метрик любого сохранённого прогона по его папке даёт те же числа (100%).
- **SC-003**: Сводная таблица строится одной командой менее чем за 10 секунд при 100 прогонах.
- **SC-004**: Собранный архив сабмита совпадает с образцом сайта по составу файлов и полей и
  содержит 100% идентификаторов закрытого теста.
- **SC-005**: Ни один повторный `final`-прогон той же конфигурации не попадает в сводку без
  записанного обоснования.

## Assumptions

- Точная формула F1 и потокенной accuracy для NER — как в библиотеке, которую использует
  официальный скрипт (seqeval, режим по умолчанию); детали — на этапе plan.
- «Конфигурация» прогона определяется подходом, моделью и параметрами без учёта роли и
  данных; её отпечаток вычисляется автоматически.
- Overall считается только по пяти задачам статьи; RuMedTest в Overall не входит (как в
  статье), его результат — отдельная строка сводки по итогам сабмита, вносимого вручную.
- Previous art: таблица 3 статьи, README репозитория (RuBioBERT/RuBioRoBERTa),
  `lb_submissions/SAI/ChatGPT` (DaNet 89.3, NLI 61.3, RuMedTest 35.0 — на закрытом тесте сайта;
  в сводке помечаются отдельно, т.к. посчитаны на другом тесте).
- Результаты на закрытом тесте сайта (если сабмит будет оценён) вносятся вручную как отдельные
  записи с источником «medbench.ru».
- Спека 001 смержена или доступна в той же ветке: харнесс использует `get_role`.
